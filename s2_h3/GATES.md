# Gate soundness — the shared-failure-mode defect

Three gate failures in this campaign had three different symptoms and one identical cause: **the measurement shared a
failure mode with the object being measured**, so the gate could not see the defect it existed to catch.

| # | symptom | shared failure mode | what it took to detect it |
|---|---|---|---|
| 1 | `npu_rotary_mul` "parity failure" (grad rel 1.3) | my interleaved-table cache was keyed on a *temporary's* `data_ptr()`; the allocator handed the same block back for the kv table | reasoning about allocator lifetimes; the gate compared two runs that both used the poisoned cache |
| 2 | SDPA per-step loss gate failed at 8.33 % | the change perturbs dropout RNG order, so per-step loss compares two different realisations of the same function | deterministic eval parity (loss rel 2.93e-06) |
| 3 | Win 2 admitted with the dW kernel returning (K,C) instead of (C,K) | **the reference was built on the same broken stage** (`dwconv_dw_ntc` on both sides) | per-parameter gradient parity against the bmm path (rel 1.22) |

A loss-only gate is structurally incapable of catching a backward bug: the forward was fine in case 3. An instrumented
profile could not measure h2d (the same run reported forward 139.9 ms against 79.1 ms uninstrumented). And in cases 1 and
3 the comparison baseline contained the defect.

## Rules that follow

1. **Reference independence.** The comparison baseline is always the frozen independent path **with no Triton install**
   (eager or the validated bmm path), never "current tree minus this change". A reference built on the same stage is not
   a reference. Frozen references live in `profile/*.json` and are never regenerated by the thing under test.
2. **Gradient parity is part of tier 2, not an optional extra.** Any kernel that changes reduction order or accumulation
   grouping must show **per-parameter gradients** against the independent baseline. Bar: worst real gradient rel
   **<= 9.2e-03** (bf16 level, measured for the corrected ntc dW). Loss-only evidence cannot admit such a kernel.
3. **Different summation order = tier 2 by default.** Tier 2 = (i) deterministic eval parity (loss rel <= 1e-5) **and
   per-parameter gradient parity**, (ii) window mean within 1 % of the reference window mean **and** slope within noise,
   (iii) a frozen new-order reference so later changes have both anchors.
4. **A number produced while a since-corrected kernel was installed is void as a number.** Re-measure, do not reason
   from it.

## Contamination record (Win 2 orientation bug, `17793b2`)

`dwconv_dw_ntc` was numerically wrong from when it landed until `17793b2`. Void as numbers: every optimization-phase
profile and gate after that landing (including the 222.1 / 222.5 ms figures, superseded by the corrected **223.7**) and
the 200 steps of `runs/swiglu5233`.

Unaffected: `out/H3/ema-50000.pt` (2026-11-26 07:48, thirteen hours before the kernel landed — no trained checkpoint ever
ran the broken gradient), and `runs/H4s/resume-5000-swiglu.ckpt`, which is a row permutation of the pre-existing
5000-step checkpoint and never ran a gradient.

**`runs/swiglu5233/ema-5200.pt` is legal as an export round-trip artifact and is FORBIDDEN as a numerical reference** —
it was produced by the broken kernel.

## Still true from earlier rounds

- Per-step loss is the tier-1 gate for changes that do not perturb RNG consumption or reduction order.
- `loss_curve.csv` needs `--loss-history-interval 1` for one row per step.
- Do not derive targets from `sum(self_device_ms)`: it under-counts device time by ~26 % on this model. Wall clock and
  the async timeline only.
