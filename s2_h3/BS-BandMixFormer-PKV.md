## 2. 设计依据：先做审计，再动结构

H3 的每一层形状都来自**冻结权重干预**（不重训，直接改前向，测配对 ΔSI-SDR），不是猜的。
协议：56 窗 / 28 窗、逐窗配对、20000 次 bootstrap 的 95% CI。

### 2.1 静态带混合能替代动态注意力吗（0–2 层）

| 干预（0–2 层） | 冻结 ΔSI-SDR 中位 |
|---|---:|
| 静态带混合（每头 62×62 固定矩阵，恒等+小噪声初始化） | **−0.02 ~ −0.04 / 层** |
| 组级混合 | −4.3 |
| 完全去掉（static 全分辨率） | −8.5 |

结论：0–2 层的跨带路由**不需要动态**，固定混合几乎无损。这一条直接支撑了 0–2 层改成 `StaticBandMixer`。

### 2.2 3–5 层能降到什么分辨率

| 能把什么降下来 | 31 组 | 12 组 |
|---|---:|---:|
| 只有值（post） | −0.38 | −1.46 |
| K/V 池化、query 逐带（`xres`） | −0.67 | −3.54 |
| Q/K/V 全池化（`gavg`） | −1.82 | −4.33 |

结论：**query 必须逐带**；K/V 降到 31 组只掉 0.67，但**尾部重**（p10 −3.49），所以最终没用。DLSS 式"低分辨率 token 同时做 query 和 key"的多级结构**不被证据支持**。

### 2.3 FFN 的帧率

| 变体 | 中位 |
|---|---:|
| `ffpool2_all` | −3.66 |
| `ffpool4_all` | −11.57 |
| **`ffpool4_L3.4.5`** | **−0.31** |
| `ffinterp4_all`（插值） | −13.17 |

结论：0–2 层的 FFN 是逐帧主力（第 0 层 FFN 输出是残差的 0.94，注意力只有 0.08），帧率动不得；3–5 层可以 4 帧一次（−0.31，28 窗全在 −0.76 内）。插值比块内广播更差——FFN 输出在时间上不线性。

### 2.4 组合后的冻结下界（D3 = 最终选定形状）

| 组合 | 0–2 层 | 3–5 层 | 中位 | p10 | 最差 | < −1 dB 的窗 |
|---|---|---|---:|---:|---:|---:|
| D | static | xres31 + ffpool4 | −1.22 | −4.85 | −10.62 | 19/28 |
| **D3** | static | **poolqk4 + ffpool4** | **−0.55** | **−1.41** | −6.43 | **4/28** |
| D4 | static(仅0–1) | xres31 + ffpool4 | −1.12 | −4.18 | −9.10 | 15/28 |

D3 的频率轴 GEMM 353 → 124.5 GFLOP（−65%）。**冻结下界 −0.55 / p10 −1.41** —— 这是"不重训、硬套结构"的代价，训练后的真实结果见 §4。

### 2.5 每层最终设计

| | 0–2 层 | 3–5 层 |
|---|---|---|
| 跨带路由 | 固定（每头 62×62） | 动态、逐带 query |
| 路由帧率 | — | 每 4 帧一次（−0.15） |
| K/V 带分辨率 | — | 全分辨率（31 组尾部太重） |
| V/out 宽度 | 窄 | 窄 |
| FFN 帧率 | 必须逐帧 | 每 4 帧一次 |
| RoPE | 不需要 | 需要（−0.3~−0.5/层） |

## 3. 结构与参数

每层 = 一个频率模块 + 一个 FFN；时间轴与 H2 相同（4 个 MSC + 第 0、4 层 PooledKV）。

| | 0–2 层 `StaticBandMixer` | 3–5 层 `SlowBandAttention` |
|---|---|---|
| 结构 | RMSNorm → to_v(192→192) → 每头一个 62×62 带矩阵 → dropout → 门控 → to_out | q/k 在 4 帧均值 token 上算（先池化再归一化，RoPE 走原版函数），块内共享；v 逐帧 128 维 |
| FFN | 原版，逐帧 | `BlockFeedForward`：4 帧均值 token 上算，块内广播 |
| 投影偏置 | 无（与 H2 一致，门控带偏置） | 无 |

**本地验证**（`h3_local_check.py`，CPU）：
- 结构：两次构建逐位相同；前后向通过；每个可训练参数有梯度；事件顺序 TF×6；块长非 4 的倍数、batch>1 均正常
- 等价性：新模块加载 H2 权重后，stride=1 与原版注意力差 6e-8；stride=4 + 块 FFN 与冻结 oracle 输出差 6e-8，SI-SDR 相同（11.445 dB）
- **途中修正**：投影第一版带了偏置（H2 没有），映射权重时留下随机偏置把路由带偏；已改无偏置

协议（与 Colab 完全一致）：MUSDB18-HQ，56 窗评测，AdamW 5e-4 + StepLR + EMA，batch 24，bf16-mixed，5k 步一段共 10 段。

| 15k | 7.742 | 7.088 | −0.266 [−0.51, −0.19] | 10/46 | 6e-7 |

### 4.3 H3 vs baseline A

| 步数 | A | H3 | H3−A 配对中位 | 均值 [95% CI] | 胜/负 | p |
|---|---:|---:|---:|---|---:|---:|

## 5. 昇腾 950PR 移植

### 5.1 先被否决的那条路：在昇腾上重写训练循环（`train_ascend/`）

在搬运 Colab 代码之前，先试过"为昇腾手写一条裸训练循环"。它跑起来了、也快，但**质量封顶**，最终弃用。

**速度（做到了）**

| 指标 | 数值 |
|---|---|
| 最终 step 时间（10000 步中位） | **1154.3 ms**（相对原始 2736.7 ms，**2.37×**） |
| 目标 390–450 ms | **未达到**（差 2.6×） |
| 训练吞吐 | 51.9 步/分钟，10000 步 11643 s |
| 推理 8 s（bf16，逐段路径） | 13.85 ms（1817 个 device kernel） |
| 推理 8 s（fp32） | 17.38 ms |
| 40 步同协议归因 | fast-loss −1259.4 / iSTFT 伴随 −175.1 / 块内快速路径 −57.2 / pinned H2D −57.9 ms |

**质量（否决理由）**：用的是它自己的协议（56 窗 / 50 歌，sha1 `8a9e6137`），**与 H2 的窗口不可配对**。

| 系统 | 中位 SI-SDR |
|---|---:|
| B0 混合当人声 | −4.133 |
| B1 未训练模型 | −31.943 |
| 该配方 EMA@10k | **2.964** |
| 该配方 best（8k raw） | 3.019 |
| G4 的 H2-50k | 9.406（不同硬件/结构/协议，仅参考） |

比 B0 高 7.15 dB，但**离 9.406 差 6.4 dB**。配对分析（`h2_paired_analysis.json`）在 12k 步对 H2 的
配对中位差 **−2.81 dB**（7 胜 49 负），趋势不收敛。记录下来的结论是：**该结构在此数据量下封顶约 4 dB，需要换结构**。

**决策**：弃用这条线，改为把 Colab 代码原样搬过来只做设备无关化（§5.2）——正是这条路产出了 9.103 dB 的 H3。

**这条线留下的、后来一直在用的教训**：
- **任何自定义 kernel 进入训练前向，必须做逐参数梯度对比**，不能只比前向数值
- 昇腾（CANN 9.2.1 + Ascend950PR）**必须装 CPU-only 的 torch wheel**；不要用 pypi 默认 CUDA wheel，
  也不要让 `uv sync` 走 `pytorch-cu128` index
- `torch.npu.conv.allow_hf32` 默认 **True**（近似 TF32），fp32 数值对齐必须显式关掉，否则只有 ~4e-4
- triton-ascend 在 950PR 上能真正编译并执行，首次调用 0.7–0.8 s 是编译开销
- torch_npu 2.12→2.13 + triton-ascend 换代**没有改变**训练吞吐
- fp32 训练慢 2.4× **不是调度问题**：fp32 在这张卡上本就没有 tensor 通路

### 5.2 环境与做法

服务器实测约束：GitHub 可达 / HuggingFace 不可达（`hf-mirror.com` 可达）/ 无 ffmpeg / torch 2.13.0+cpu + torch_npu 2.13.0 + pytorch-lightning 2.6.6（**没有 NPU 加速器**）/ `/workspace/musdb18hq` 是原始 WAV（不是 Colab 的 MP3 解码件）。`train_ascend/` 那条裸循环重写路线的结果不可与 Colab 曲线相提并论（见 §5.1）。

做法：Colab 代码原样搬，只做设备无关化——`entry.py`（`install_npu_trainer()` 注册 `npu` 加速器 + `MixedPrecision('bf16-mixed','npu')` + `SingleDeviceStrategy`）、`stage.py`、`prepare.py`/`run_h2.py`。CUDA 路径逐字不变，本机 CPU 回归仍然 `PREFLIGHT_PASS`（10 个 arm）。

### 5.3 数据一致性闸门（这段本身就是一次实验）

第一版闸门用 **CRC32 逐位比对**，结果 `PROTOCOL_FAIL`。逐项排查（每种假设都验证到"0/112 窗匹配"）：

| 假设 | 结果 |
|---|---|
| MP3 解码器差异 | 已排除 |
| 重采样路径 | 已排除 |
| 帧切分/填充 | 已排除 |
| **解码算术（浮点累加顺序）** | **成立** |

改用**逐样本参照**（Colab 导出 56 窗的 float16 PCM 参照）后：

| 量 | 实测 | 判据 |
|---|---|---|
| 有差异的样本比例 | 均值 0.0727%，最大 0.1539% | ≤2% → 通过 |
| 窗能量差 | ≤2.4e-6 相对 | — |
| 最坏单样本差 | 4.9e-4 = 16 PCM16 LSB（参考值本身很响，该处一个 f16 量子就是 16 LSB） | 原判据 1 f16 ulp → 不过；改为 16 LSB → 通过 |

**判据本身经过了重新论证**：0.0727% 的样本有差异（远低于 2% 的容差）、窗能量差 2.4e-6、差异幅度恰好是
float16 在评测分辨率下的一个量子——这是"同一数学、不同浮点顺序"，不是数据漂移。判据改为
"每样本 ≤16 PCM16 LSB 且差异能量 ≤1e-9 窗能量"后 `PROTOCOL_PASS`。**教训：逐位 CRC 在浮点解码链上是过严的判据**，会把你引向"数据错了"的错误结论；应该用逐样本、带分辨率的判据。

### 5.5 Triton 内核：1 个采纳，5 个否决

**采纳：`dwconv_dw`（深度卷积的权重梯度）**

| | |
|---|---|
| target | `Conv3DBackpropFilterV2` = 496 ms / 1169 ms（42%），profile rank-1 |
| kernel | `_dw_dw`：每 program 一个（channel block, row split），3-D `(c,k,t)` tile，fp32 累加，atomic add |
| config | `bc=1, bt=128, bk=32, ns=4` |
| bf16 数值 | 1.7e-3 rel（限 1e-2）通过 |
| fp32 数值 | 5.7e-07（对 float64 参照，限 1e-5）通过；对 eager 是 2.9e-04，因为 **eager 自己对 float64 就差 2.9e-04** |
| 速度 | **62.7 ms vs 127.1 ms eager（2.03×）**，ABBA，20 次中位 |
| 整步 | 0.00110775 vs eager 0.00110775，相对差 0.0e+00 |

**否决（记录在案）**

| 目标 | 失败原因 |
|---|---|
| dwconv forward | 编译失败：tile `(c,k=31,t)` 是输出的 31 倍，需 442 KB / 只有 221 KB UB |
| dwconv forward（按 tap 循环） | 慢 370×：每个 tap 重读整行，21.4 万个小 program 的调度成本超过算术 |
| dwconv dX | 与 forward 同两种失败模式 |
| 整个卷积一起 Triton 化 | 把 fwd+dX 算进去后输给 eager（0.59–1.45×） |

**最终配置**：`S2_TRITON=dwconv_dw_bmm` + 训练中融合 `F.rms_norm` + pin-memory → **627 ms/步**（eager 1112.6，1.78×；Colab T4 2580，4.1×）。

## 6. CPU 推理快路径（本轮工作）

协议：NAS 上的 EPYC 7532，`taskset -c 0-7`（单 NUMA 节点），torch 2.15.0+cpu / py3.11.2，FP32，batch 1，
输入 1×2×**352800**（8 s stereo，690 帧），权重冻结。基线 **2769 ms**（记录值 2.7700 s，RTF 0.351）。

### 6.1 基线到底花在哪

分段（每 8 s）：freq[0..5] 268/266/263/221/196/211 = **1426 ms**；temporal[0..5] 96/204/199/197/79/197 = **972 ms**；
mask_head 134；band_split 19；final_norm 13；其余（STFT/ISTFT/掩码应用）约 206。

按算子 self 时间：

| 算子 | ms | 类别 |
|---|---:|---|
| `addmm` | 515 | GEMM |
| **`copy_`** | **500** | 纯搬运 18% |
| `mm` | 373 | GEMM |
| `mul` | 292 | 逐元素 |
| `add` | 204 | 逐元素 |
| `mkldnn_convolution` | 171 | 卷积 |
| `gelu` / `cat` / `bmm` / `baddbmm` / `silu` / `div` / `linalg_vector_norm` / `index_select` | 85/82/74/67/55/51/48/31 | — |

**只有 37% 是真 GEMM，一半时间在搬运和逐元素上。**

### 6.2 采纳的改动（7 项代码，全部数学等价）

| 改动 | 位置 | 效果 | 数值 |
|---|---|---|---|
| 深度卷积改走 2-D channels_last | `entry.py::conv_forward` | **42.1 → 11.6 ms/次** | max\|Δ\| = 0（逐位） |
| 去掉 conv 前多余的 `contiguous()` | `entry.py::MSC.forward` | −110 ms | — |
| MSC 每层少一次跨步拷贝，`proj_out` 走 matmul | `entry.py::MSC.forward` | 每层 165 → 99 MB 流量 | 梯度相对 8.4e-6 |
| `SlowBandAttention` 去掉 267 MB/层广播 | `h3.py` | −42 ms | max\|Δ\| = 0 |
| 注意力输出保持连续布局 | `pooled_kv.py`、`entry.py` | −83 ms | 相对 5.4e-07 |
| RMSNorm 用融合核 | `transformer.py` | −110 ms | 相对 4.9e-07 |
| RoPE 去 `cat` | `transformer.py` | −80 ms | max\|Δ\| = 0 |

运行期开关在 `transformer.FAST`，`ablate.py` 可在单进程内交替消融。

### 6.3 零代码的环境收益（更大）

| 设置 | 效果 |
|---|---|
| `OMP_PROC_BIND=close OMP_PLACES=cores` | 线程原来跨 8 个 NUMA 节点漂移；**−1.24×** |
| `MALLOC_MMAP_THRESHOLD_/TRIM_THRESHOLD_` 调大 | 大张量不再每次 mmap + 缺页，改复用堆；**−1.08×** |

两者合计 3009.9 → 2422.2 ms（同会话内）。

### 6.4 核心放置：同样是 8 个核，1.19×

这台机器 8 个 NUMA 节点 / 8 个内存控制器，原协议把 8 线程全放节点 0：

| 核心 | `OMP_PROC_BIND` | 时间 / 8 s |
|---|---|---:|
| `0-7`（单节点） | close | 2303.1 ms |
| `0-7`（单节点） | spread | 2284.4 ms |
| `0,8,16,24,32,40,48,56` | close | 1979.7 ms |
| `0,8,16,24,32,40,48,56` | spread | **1941.6 ms** |

收益来自核心集合，不是绑定策略。**机制用 400 MB 工作集（远超 128 MB L3）的纯带宽测试坐实**：

| 8 线程 / 400 MB | 单节点 | 分散 8 节点 | 比值 |
|---|---:|---:|---:|
| `copy`（读+写） | 11.5 GB/s | **17.5 GB/s** | 1.52× |
| `add`（2读+1写） | 12.8 GB/s | **16.5 GB/s** | 1.29× |
| `sum`（纯读） | **22.6 GB/s** | 17.1 GB/s | **0.76×** |

**写变快、读变慢。** 模型是写密集的（每个逐元素算子都新分配并写满 33 MB 张量），写流量分散到 8 个控制器就快；
纯读时数据归某个节点所有，跨节点读要过 Infinity Fabric 反而更慢。这同时解释了 §6.6 的"收益不叠加"——
瓶颈是**写带宽**，不是算子数量。

⚠️ **这是协议问题，不是技术问题**：单节点代表消费级 8 核（1 个内存控制器、~50 GB/s 总量），
分散 8 节点代表"64 核服务器只开 8 线程"。两者差 1.19×，取哪个由部署形态决定。

### 6.5 最终数字

| 配置 | 时间 / 8 s | RTF | 相对 2769 |
|---|---:|---:|---:|
| 原始基线（8 核单节点） | 2769 ms | 0.351 | 1.00× |
| **代码 + 环境** | **2202 ms** | **0.275** | **1.26×** |
| 代码 + 环境 + 8 节点分散 | 1941.6 ms | 0.243 | 1.43× |
| 代码 + 环境 + 16 线程 | ~1890 ms | 0.236 | 1.47× |

24 线程不再提升（带宽饱和）。

### 6.6 试过但不成立的路（都留了数字）

| 尝试 | 结果 | 结论 |
|---|---|---|
| 逐项消融三项改动 | 单开各 1.01–1.04×，全开仍 1.02–1.04× | **收益不叠加**，瓶颈在写带宽上转移 |
| `torch.compile`（inductor + zig + libiomp5） | **1.01×**，首次编译 452 s | 该图 reshape 太多，inductor 不融合，放弃 |
| shift-add 替代深度卷积 | 717 ms（vs conv1d 42 ms） | 31 遍全张量读，被带宽打死 |
| 分块 shift-add（t=32/64/128） | 54–67 ms | 仍输给 channels_last 的 11.6 ms |
| `conv2d` channels_last（batch=1 测的） | 假数据 0.18 ms | **形状错了**，见 §7 |
| 24 线程 | 1885.6 ms ≈ 16 线程 | 带宽饱和 |

### 6.7 天花板（硬账）

- GEMM：262.6 GFLOP，`addmm` 实测已到 **300 GFLOP/s**（8 核 Zen2 实用峰值）→ 下限 **750–870 ms**
- 逐元素/搬运：已是 **10–30 GB/s** 的节点带宽上限，完美融合下限 ~400 ms（且无编译器可用）
- 合计下限 ≈ **1.1–1.2 s，RTF 0.14**

**0.125 在 8 核上靠实现到不了。** 需要再砍 20–30% FLOP（FFN 占 151/262 GFLOP，是最肥的一块），
或换更小的模型——那是训练决策，要重跑 50k 并用 §2 的冻结权重法量质量代价。

## 7. 测量纪律（这一轮踩的坑，全部记录）

这些错误都产生过"看起来很好"的假数字，写在这里避免重复：

1. **输入长度**：RTF 协议是 352800（8 s = 690 帧）。用训练块 131584 会得到低 3 倍的假结论。
2. **候选必须交替跑**（ABBA / 单进程 round-robin）。串行跑时后一个吃到预热和频率红利——曾让
   "channels_last 1.17×" 这个**纯假象**通过检查；`max|Δ| = 0` 恰恰证明它什么都没改。
3. **用 `torch.no_grad()` 不是 `torch.inference_mode()`**：模型里自定义 autograd 函数在后者下会报错。
4. **先确认形状再信数字**：`fastbench.py` 里 `F_=1` 的老 bug 让 conv 候选跑在 1 行上（标签写着 62），
   得出 1.09 ms；真实值 42.1 ms，差 40 倍。
5. **缓存内测不出 DRAM 行为**：33 MB 工作集的"带宽"测出 13 TB/s（物理不可能），必须用远超 L3 的工作集。
6. **逐位 CRC 不适合浮点解码链**：见 §5.2，会把你误导成"数据错了"。
7. **单位统一**：写"每 8 s 块"，不要混"每 24 s"，混用差 3 倍。

## 8. 结论

**站得住的：**

1. H3 的频率轴结构有完整的冻结权重证据链（§2），不是拍脑袋；每层形状都能追到一次干预实验。
2. 速度目标达成：H3/A = 3.06×，H3/H2 = 1.85×，MACs 262.6 GFLOP（比 A −71%）。
3. 质量：与 baseline A **统计平手**（50k 配对中位 +0.003，p=0.6），比 H2 **差 0.34 dB**（p=2e-8，48/56 窗输）。
4. 评测平台可以排除（同权重换平台差 0.001 dB）。
5. 昇腾移植成功：数据闸门 `PROTOCOL_PASS`，1 个 Triton 内核采纳（2.03×），整步 627 ms（eager 的 1.78×）。
6. CPU 推理 1.26×（8 核单节点 0.351 → 0.275）纯免费，全部数值验证；核心放置再给 1.19×。
7. 天花板算清了：8 核下限 RTF 0.14，0.125 需要砍 FLOP 或换小模型。

**被否决、但值得记一笔的：**

0. "在昇腾上手写训练循环"这条线（§5.1）速度做到 1154 ms/步（2.37×），但质量封顶 ~3 dB，
   离 H2 的 9.406 差 6.4 dB，配对分析 −2.81 dB 且不收敛。结论：该配方在此数据量下天花板太低。
   真正的解法是**不重写**——把 Colab 代码原样搬过来只做设备无关化，这条才产出 9.103 dB。

**没解决的：**

1. **训练平台混淆未排除**：H3 在 NPU 训、A/H2 在 Colab T4 训。需要 H2 在 NPU 上训一遍才能把
   "架构差 0.34 dB" 和 "平台差" 分开。这是唯一挡在结论前面的问题。
2. H3 的 0.34 dB 是否值得 48% 的算力节省——这是产品取舍，不是技术问题。
3. CPU 上要到 0.125，必须做 FLOP 削减（分组 FFN 候选：3–5 层 FFN 已可 4 帧一次，0–2 层动不得）+ 重训 + 质量评估。

**一句话**：BS-BandMixFormer-PKV 是一个"用 0.34 dB 换 48% 算力"的结构改造，设计有据、实现等价、速度达标；
它不是免费升级，是否采用取决于部署对质量与算力的边际估值。
